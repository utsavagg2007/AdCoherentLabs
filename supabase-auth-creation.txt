Target architecture:
- The frontend authenticates only against our self-hosted Supabase Auth.
- The frontend sends the Supabase access token to the existing backend using:
  `Authorization: Bearer <access-token>`
- The backend validates every protected request.
- The backend derives the authenticated user from the verified JWT `sub` claim.
- The backend maps the Supabase user UUID to the existing application user.
- The backend derives the active tenant from validated membership data.
- Every tenant-owned query and mutation must enforce tenant boundaries.
- Authorization must be deny-by-default.
- Authentication and authorization must be separate concerns.
- A valid user must not automatically receive access to every tenant.
- If this application uses SSR or a BFF pattern, prefer secure HttpOnly, Secure, SameSite cookies and explain the CSRF protection strategy.

JWT validation requirements:
- Validate signature, issuer, audience, expiration, and not-before claims where applicable.
- Detect the actual signing-key strategy used by the deployed Supabase version.
- For asymmetric signing, use the self-hosted JWKS endpoint and a maintained JWT library.
- For legacy HS256, use the safest supported server-side validation approach.
- Never merely decode a JWT and trust its contents.
- Support signing-key rotation.
- Reject tokens from another project, issuer, environment, or audience.
- Never log access tokens, refresh tokens, authorization headers, passwords, reset tokens, or secrets.

SaaS tenant-isolation requirements:
- Model organizations/workspaces/tenants explicitly.
- Model memberships separately from users.
- Use explicit roles and permissions.
- Add unique constraints and foreign keys that prevent cross-tenant relationships.
- Derive tenant context from authenticated membership, never from an untrusted request body.
- Check tenant membership on every read, write, update, delete, export, and download operation.
- Prevent IDOR, horizontal privilege escalation, vertical privilege escalation, and tenant breakout.
- Ensure background jobs, webhooks, scheduled jobs, exports, and admin tools also enforce tenant boundaries.
- Define a secure platform-admin path separately from tenant-admin access.
- Add authorization tests for same-tenant, cross-tenant, regular-user, tenant-admin, and platform-admin scenarios.

Security requirements:
- Enforce strong password and email-verification policies.
- Add rate limiting and abuse protection to signup, login, password reset, verification, and invitation flows.
- Implement session expiration, refresh-token handling, logout, revocation, and concurrent-session behavior.
- Support MFA for privileged users and sensitive actions if supported by the deployed Supabase version.
- Require step-up authentication for changing email, password, MFA, ownership, billing, API keys, or tenant membership.
- Use secure cookie settings where cookies are used.
- Configure strict CORS allow-lists.
- Add CSRF protection where cookie authentication is used.
- Prevent open redirects in login, reset, invite, and OAuth flows.
- Validate all input server-side.
- Use parameterized queries and existing ORM protections.
- Add security headers where appropriate.
- Review SSRF, XSS, SQL injection, CSRF, request smuggling, file-upload, webhook, and dependency risks.
- Never allow client-controlled role or tenant changes.

Privacy requirements:

- Classify data as public, internal, confidential, or sensitive.
- Collect only data necessary for the product.
- Do not place PII, tokens, passwords, or secrets in logs.

Audit and operational requirements:

- Include tenant, actor, target, action, outcome, timestamp, request ID, and source where appropriate.
