The three detection channels, in order of precision. The Federal Register API (federalregister.gov/api/v1/documents.json, filtered to final rules from your tracked agencies) is your push signal — each document carries its CFR references and an effective_on date. The eCFR versions endpoint (/api/versioner/v1/versions/title-12.json) lists per-section amendment dates, so a daily diff against your stored version table tells you exactly which §§ changed — you re-ingest three sections, not three titles. States and FINRA have no changelog, so they get scheduled scrapes (most state amendments take effect in Jan 1 / Jul 1 clusters after sessions end) with a SHA-256 comparison per section; only changed hashes get re-parsed and re-embedded. LegiScan or OpenStates bill-tracking against your manifest citations makes a good early-warning layer later.
The detail that matters most for a compliance product: publication date ≠ effective date. When the FR API surfaces an amended §1026.24, ingest the new text immediately but flag it with its future effective_start — don't wait, and don't overwrite. That turns a plumbing problem into a product feature: "this ad passes today but violates the amended Reg Z advertising rule effective October 1" is exactly the alert a compliance lead pays for.
Which is why the storage layer never updates text in place. A regulation_versions table with effective_start / effective_end per section, chunks foreign-keyed to a version: live checks filter to currently-effective rows, audit replays filter by the ad's run date, and superseded text stays queryable forever. Store the embedding model name on each chunk too, so a future model swap becomes a lazy re-embed instead of a migration. And after every update run, fire a small canary set — a golden list of citation lookups ("retrieve the APY advertising rule") — so a broken state scraper or a changed XML schema fails loudly in CI instead of silently degrading verdicts.
